# Contribution

The 2004 nanopass paper got accepted to ICFP only after the program committee made the
authors reframe it as *education*, because they did not believe many-small-passes could
survive commercial compile-time budgets. This paper is the reply, nine years later, with
data. The claim under test: replace the five back-end passes of the 10-pass Chez Scheme
compiler with roughly 50 nanopasses over roughly 35 intermediate languages, keep 100%
compatibility, and stay within 2x compile time.

Outcome: compile time 1.64-1.75x, generated code 15.0-26.6% *faster* than the original, and
the new compiler passes the full Chez test suite plus the bootstrap-consistency check. The
speed win is not attributed to nanopass structure — it comes from a graph-coloring register
allocator that nanopass structure made tractable to build, plus improved closure optimization
and cross-library optimization.

The framework itself is the second contribution: `define-language` and `define-pass` as a
DSL where languages are context-free grammars, passes autogenerate the boilerplate for every
production they do not mention, and the compiler writer only writes the interesting clauses.

# Mechanism

**`define-language`** is a grammar: terminals (each needing a visible `name?` predicate),
nonterminals with meta-variables, and productions. Three production shapes: a bare
meta-variable (`x` — a uvar is an Expr), a keyword-led S-expression (`(if e0 e1 e2)`), and an
implicit S-expression with no keyword (`(pr e* ...)`). Keywords are allowed only in head
position. `=> (e e* ...)` attaches a pretty form used by the autogenerated unparser. The `*`
suffix plus `...` is the plurality convention.

**`define-language` with `extends`** is the thing that makes 35 languages affordable. Only
the delta is written:

```scheme
(define-language L1 (extends Lsrc)
  (terminals (- (datum (d))) (+ (constant (c))))
  (Expr (e body) (- (quote d)) (+ (quote c))))
```

Removing `datum` unbinds the meta-variable `d`, so a stale `(quote d)` production left behind
is a compile-time error, not a latent bug. The grammar delta typechecks the pass.

**`define-pass`** has a signature `: Lin (formals) -> Lout (extra-returns)`, a `definitions`
clause scoped alongside the transformers, one transformer per nonterminal pair
(`Expr : Expr (ir) -> Expr ()`), and a body. Inside a transformer, clauses are
pattern/optional-guard/expressions. Patterns come from the input grammar; pattern variables
are unquoted (`(quote ,d)` binds `d`). Output is built with quasiquote rebound to a
language-term constructor, with `,` escaping back to Scheme. Every production the author does
*not* write a clause for gets an autogenerated identity clause mapping input form to
equivalent output form. Catamorphism syntax recurs on subforms inside a pattern.

The worked example, `convert-complex-datum`, is the whole idiom in 30 lines: one clause
matching `(quote ,d)` guarded by `(not (constant? d))`, accumulating into `const-x*`/`const-e*`
via `set!`, returning a fresh temp; then the pass body wraps the result in a `let` binding all
the lifted constructions. Everything else in the language is handled by generated code.

**Changes from the 2004 prototype.** Languages may be defined anywhere a definition can
appear, not just top level. Passes may omit an input or output language, so parsers,
predicates, and code generators are also passes. Passes take extra arguments and return extra
values, so analysis results flow without being encoded into the language term.
`with-output-language` constructs terms outside a pass; `nanopass-case` matches outside a
pass. Dispatch moved from record dispatch to an integer tag. Clause order is now respected,
so hot patterns can go first. Less code is generated, so the compiler-compiler is faster.

**What actually changed in Chez's back end.** The original five: `cp1` (starts closure
conversion, recognizes loops and direct lambda application, multiple-value returns, foreign
entry, primitive-to-inline), `cpr0` (starts register allocation, real free variables after
closure optimization, assignment conversion, flags tail calls and loops), `cpr1` (initial
register homes), `cpr2` (saves/restores around non-tail calls, redundant binding removal),
`cp2` (inline primitives to instruction inlines). It used linear-scan allocation with the
Burger-Waddell-Dybvig lazy-save strategy, destination-driven code generation, and reserved two
or more registers for the assembler because primitive expansion is delayed to code generation.

The new compiler switched to **graph coloring with move biasing**, and that one decision
forced structural change: near-assembly form must be reached much earlier so every temporary
the final operand constraints require actually exists, and a full live analysis over
*variables* is now needed to build the conflict graph. The original dodged that by tracking
liveness of *registers*, not variables. Graph coloring packs spilled variables tighter on the
frame and produces more compact code, which is where the run-time win comes from, especially
on 32-bit x86 with eight registers.

# Applicability

Preconditions: a language with real macros. The framework is a DSL implemented as syntactic
abstraction, and its value depends on generating boilerplate at expansion time. There is no
runtime interpretation cost; the generated dispatch is an integer tag compare.

Costs, measured and specific: compile time 1.71/1.75 (x86/x86-64, opt 2) and 1.64/1.71 (opt
3). But those averages hide a range of 1.00 to 4.73 per benchmark. The authors checked
whether the outliers correlate with expanded source size and found *no direct relationship*
(Figure 4), and say plainly they do not understand why. That is an unexplained result sitting
in the middle of the paper's central claim.

The comparison is also not apples-to-apples and they say so: they lacked resources to build a
second nanopass compiler matching the old one's function, so the 1.75x figure bundles
nanopass overhead with the deliberately slower graph-coloring allocator. The nanopass tax
alone is unmeasured.

Two regressions are disclosed. Block allocation of closures (one allocation for a group of
simultaneously created closures) is missing from the new compiler. And the new register
allocator replaces lazy saves with a heuristic estimating save/restore cost against permanent
frame spill cost, which "sometimes underperforms the original."

# Relevance

This is the framework our compiler is built in, so the mechanism section above is
specification, not background. Three things bear directly on how we sequence phase 7.

First, `extends` is why a 13-stage pipeline with a language per stage is affordable rather
than absurd. Our CUJ defines `Lcore` once with `declare` and `policy` forms; every later
stage should be an `extends` delta from its predecessor, so that removing `declare` after
stage 06 consumes it becomes a one-line grammar change that then *fails to compile* any later
pass still referencing it. That is the mechanism by which "the policy lives in the environment
threaded through the passes, not in a global parameter" gets enforced rather than merely
intended.

Second, "passes take additional arguments and return additional values" is the sanctioned way
to thread our abstract domain through stages 05 and 06 without polluting the language term
with analysis results. Interval and pentagon facts should ride as extra return values, not as
annotations in the grammar. If we find ourselves adding an `absval` field to a production, we
have chosen wrong.

Third, and most usefully, this paper contradicts the CUJ's stage 12 plan with evidence. The
CUJ specifies linear scan. Chez's *original* compiler used linear scan with lazy saves; the
*new* one moved to graph coloring with move biasing, and that change is named as "the biggest
contributing factor, and the one that is consistent in all of the benchmarks" for a 15-27%
speedup. The 32-bit x86 case (eight registers) benefited most, which is the register-pressure
regime our AVX-512 loop bodies will not be in, but our general-purpose integer code will. The
honest read: linear scan is the right *first* implementation because it is simple and fits the
tree, but the ceiling is measurably higher with coloring, and Chez paid for it in compile time
deliberately. Worth planning stage 12 with a swappable allocator interface from the start.

Also note what the new compiler had to give up to get coloring: near-assembly form much
earlier, and a full variable-liveness pass. That is an argument for keeping stages 11 and 13
close together and for not assuming register allocation can stay an AST-shaped pass forever.

**Slug and identity check.** Title page: *A Nanopass Framework for Commercial Compiler
Development*, Andrew W. Keep (University of Utah) and R. Kent Dybvig (Cisco Systems Inc.),
running footer `2013/9/20`, and the copyright block reads "[Copyright notice will appear here
once 'preprint' option is removed.]" So this is genuinely the author preprint, not the
published ICFP 2013 version. The slug's `-preprint` suffix is accurate. Note Dybvig's
affiliation is Cisco, not Indiana — Chez had been acquired by then, and Section 2 says
outright that "the Chez Scheme compiler is not open-source," which is why every code example
comes from a student compiler instead. (Chez was open-sourced in 2016, after this paper.)

**Not a duplicate of `keep-a-nanopass-framework-for-commercial-compiler-developm.pdf`.** That
file shares the exact title but is Keep's 170-page Indiana University PhD dissertation,
December 2012, cited here as reference [14]. Two distinct works. Anyone deduplicating by
title will merge them wrongly.

The most interesting thing in the paper is the thing it does not resolve. Compile-time
overhead ranges from 1.00x to 4.73x across benchmarks with no correlation to program size,
and the authors say an understanding of why "might lead to overall improvements." That is a
real open question about nanopass compilers and it is worth watching for in our own build:
if some of our benchmarks compile 4x slower than others of similar size, this paper says that
is a known, unexplained phenomenon rather than a bug in our passes.

Mild overselling in the abstract: "produces faster code than the original, averaging 15-27%"
is true, but the paper attributes it to the register allocator and closure optimization, not
to nanopass structure. Nanopass made the rewrite *feasible*; it did not make the code fast.
The two similix/softscheme benchmarks actually got 1.22-1.54x *slower* because they invoke the
compiler at run time, and the authors flag this as dragging the average down — which cuts the
other way and is honestly reported.
