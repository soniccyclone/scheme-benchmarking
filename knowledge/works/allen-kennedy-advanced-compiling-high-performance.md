# Contribution

This is the canonical statement of the *dependence-based* approach to compilation: build one relation over statement instances that captures every ordering constraint the program's semantics actually require, prove that any reordering preserving that relation preserves meaning, and then derive every loop transformation as a legality question about that relation. Everything else in the book is a consequence.

The three things it supplies that nothing else in our bundle does:

1. **A complete dependence-testing suite** (ch. 3), organized by subscript complexity rather than by mathematical machinery. Most treatments present Banerjee's inequality and stop. This one partitions the problem first and applies the cheapest exact test that fits, which is why it is fast enough to ship.
2. **The loop-based vectorization tradition** (ch. 2, 5), centered on `codegen`, a recursive strongly-connected-component algorithm that is roughly ten lines and does the whole job. This is the tradition Larsen and Amarasinghe were arguing *against*, and having both sides on file is the point.
3. **Induction variable substitution as a standalone algorithm** (ch. 4), with the dominance preconditions, the self-edge recognition test, and the def-use graph repair spelled out in pseudocode.

The theoretical spine is Theorem 2.1 (Fundamental Theorem of Dependence: any reordering transformation preserving every dependence preserves meaning, proved by exhausting the three ways a statement can read a wrong value) plus Theorem 2.3 (a transformation not altering loops 1..k preserves every level-k dependence). Those two theorems are what make loop-by-loop reasoning legal at all.

# Mechanism

**Dependence representation.** A statement instance is named by an *iteration vector*, one entry per enclosing loop, ordered lexicographically. For a dependence from instance `i` to instance `j`, the *distance vector* is `d(i,j)_k = j_k - i_k` and the *direction vector* replaces each entry with `<`, `=`, `>`. The leftmost non-`=` entry must be `<` or the "source" executes after the sink, which is impossible. The *level* of a loop-carried dependence is the index of that leftmost non-`=` entry; loop-independent dependences get level ∞. A *direction matrix* stacks all direction vectors for a nest; permuting loops permutes its columns, so legality of any permutation is checked by inspecting the matrix, never by rewriting code (Theorem 5.1).

**Dependence testing (ch. 3).** Testing `f_i(α) = g_i(β)` for all subscripts within loop bounds is NP-complete in general (integer solutions to linear Diophantine systems). The algorithm avoids that:

1. *Partition* subscript pairs into separable and minimal coupled groups by unioning any two that share an index. Presented as O(n²) but linear with union-find.
2. *Classify* each as ZIV (no index), SIV (one index), MIV (several).
3. ZIV: form the symbolic difference; a nonzero constant proves independence and halts everything immediately.
4. SIV: split by coefficient shape. **Strong SIV** `<ai+c1, ai'+c2>` gives distance `d = (c1-c2)/a` directly; dependence exists iff `d` is an integer with `|d| <= U-L`, and this extends to symbolic bounds by comparing `d` against `U-L` symbolically. **Weak-zero SIV** (one coefficient is 0) yields a single crossing iteration `i = (c2-c1)/a1` and directly *tells you to peel* that iteration. **Weak-crossing SIV** (`a2 = -a1`) is symmetric about `i = (c2-c1)/(2a1)`; all dependences cross that point, so *splitting the loop there* removes them. An exact SIV test via extended GCD (Theorem 3.1 enumerates all solutions as `x_k = n_a(b0-a0)/g + k(b1/g)`) is given for the general case.
5. MIV: GCD test (`gcd(a_1..a_n, b_1..b_n)` must divide `b0-a0`; tighten by substituting `a_i - b_i` wherever the direction is `=`) then Banerjee's inequality, which relaxes to real solutions and applies the intermediate value theorem: a real solution exists iff `Σ H_i^-(D_i) <= b0-a0 <= Σ H_i^+(D_i)`. The trapezoidal variant handles bounds that are affine in outer indices by sweeping innermost-to-outermost and *adjusting the outer coefficients* as it goes.
6. Coupled groups: the **Delta test**. SIV results become constraints (a dependence *distance*, *line*, or *point*); constraints intersect exactly, since intersecting lines in a plane is exact; surviving constraints propagate into MIV subscripts, often eliminating an index entirely and demoting MIV to SIV, which triggers another pass. Linear in the number of subscripts. Named failure modes: propagation is inexact when an index survives in only one of the two references, triangular iteration spaces impose constraints the test does not use, and general MIV constraints are never propagated.

**Vectorization (ch. 2).** `codegen(R, k, D)`: find maximal SCCs of `D` restricted to `R` (Tarjan), contract each to a node, topologically sort, and walk in order. An acyclic node is a single statement not in any recurrence, so emit it as a vector statement in `ρ(π)-k+1` dimensions. A cyclic node gets a sequential level-`k` DO, then recurse at `k+1` with all level-`k` edges deleted, because Theorem 2.3 says running loop `k` sequentially satisfies them. Termination is guaranteed since loop-independent dependences are acyclic and carried dependences are eventually all satisfied. This is loop distribution and vectorization in one pass.

**Enabling transformations (ch. 5).** Each one is presented twice, once for safety and once for profitability, and the profitability question is repeatedly NP-complete:

- *Loop shifting* (Theorem 5.2): a block of loops carrying no dependence can always be shifted inside the next loop and will still carry none. Cheap, effective, and it slots into `codegen` as four lines.
- *Scalar expansion*: `T` becomes `T$(I)`. The dependences it deletes are computable in advance (Theorem 5.3): backward carried antidependences, all carried output dependences, and loop-independent antidependences preceding the *covering definition*, a definition such that one placed at loop entry reaches no later use. Missing covering definitions are manufactured by inserting an identity assignment `T = T`, which if dead means expansion is trivial. Storage blowup is controlled by strip-mining first and expanding only the strip.
- *Scalar and array renaming*, *node splitting* (copy a value to break a critical antidependence), *reduction recognition* (identified by the self true/output/anti triple with no other true dependences in or out), *index-set splitting* by threshold or crossing point, *run-time symbolic resolution* (annotate edges with *breaking conditions* and emit an IF-guarded two-version loop), and *loop skewing*.
- The driver (`mark_loop`, `transcode`) does all of this **on the dependence graph first**, without touching code, then replays only the transformations needed for the loops actually selected.

**Coarse-grained parallelism (ch. 6)** inverts the goal: parallel loops go *outward*. A loop can be parallelized at the outermost level iff its direction-matrix column is all `=` (Theorem 6.1). Selecting which loop to sequentialize is minimum set cover, hence NP-complete. A nest is *fully permutable* iff every dependence is carried outside the range or has only `<`/`=` in it (Theorem 6.3), and any nest with constant distances can be made fully permutable by skewing (Theorem 6.4). Interchange, reversal, and skewing are unified as unimodular matrices `T`, valid iff every row of `Td` is positive. **Typed fusion** (Kennedy and McKinley) solves fusion optimally in O(N+E) via a greedy `maxBadPrev` computation, where a bad path is one containing a bad edge or a node of another type. Fusing multiple types optimally is NP-hard, so types are prioritized and fused in descending order.

**Control dependence (ch. 7).** IF-conversion turns control dependence into data dependence: relocate exit branches out of their loops using a monotone flag `lm`, then remove forward branches by sweeping a current guard, conjoining branch conditions and disjoining target conditions. Boolean simplification is NP-complete, so a linear approximation exploits the fact that guard variables simplify out in reverse introduction order, so only ever try to cancel the most recent key variable. Backward branches need a `bb` flag distinguishing first pass from later passes. IF-conversion hurts when vectorization fails, so *IF reconstruction* is the required inverse. The alternative, kept for parallelization, is an explicit control dependence graph (Cytron's postdominator-tree algorithm, O(max(N+E, |CD|))) plus three-valued *execution variables* to preserve branch decisions across loop distribution.

**Memory hierarchy (ch. 8).** *Scalar replacement* rewrites array references as compiler temporaries so the existing coloring allocator keeps them in registers. It runs on a *pruned* dependence graph (kill flow/input edges whose value is overwritten in between; drop input edges made redundant by a common generator), and the pruning reduces to typed fusion with the array name as the type and output/anti/inconsistent dependences as bad edges. Register pressure is managed by 0-1 bin packing (O(nM) dynamic program, or greedily by `value/cost` ratio). Multi-iteration reuse needs several temporaries plus register copies, eliminated by unrolling to the permutation's cycle length. *Unroll-and-jam* (unroll outer, fuse the inner copies) is legal to factor n iff no dependence has direction `(<,>)` with outer distance `< n` (Theorem 8.1), and takes matrix multiply to `m²` flops per `2m` loads. Conditionals defeat naive scalar replacement, so initializing loads are placed by a partial-redundancy-elimination formulation using `alive`, `init`, `pinit` sets.

**Scheduling (ch. 9)** covers list scheduling with a backward critical-path prepass, trace scheduling, and software pipelining, where the kernel length is bounded below by `max_t #t/m_t` (finite hardware) and by the maximum recurrence *slope* `Σ delay / Σ cross` over cycles.

**Interprocedural analysis (ch. 10)** classifies problems on two axes: propagation vs side-effect, flow-sensitive vs flow-insensitive. Flow-insensitive side effects (MOD, REF) fall to O((N+E)V) via a *binding graph* over formal parameters, marking, then Tarjan-based reachability for globals; without the binding-graph decomposition, recursion causes a shift-register effect that iterates once per parameter. Interprocedural constant propagation reuses the single-procedure lattice algorithm over an *interprocedural value propagation graph* whose nodes are *jump functions*. The same lattice machinery, swapped for a *bounded regular section* lattice, gives array section analysis, which is what actually lets a loop containing calls be parallelized.

# Applicability

Preconditions the whole edifice rests on, stated plainly:

- **Affine subscripts in loop indices with constant coefficients.** Non-affine subscripts force the conservative assumption that every dependence exists. Ch. 4 exists entirely to manufacture this precondition via induction variable substitution, forward substitution of region-invariant expressions, constant propagation, and dead code elimination.
- **Unit stride, normalized loops** for the tests as stated. Ch. 4 warns that normalization is *not* free: normalizing `DO J = I, N` turns a `(<,=)` direction vector into `(<,>)`, which invalidates a loop interchange that was legal before. Normalization skews dependences.
- **Countable trip counts.** DO-loop bounds must be evaluated before the body; while-loop conditions re-evaluate per iteration and (ch. 7 §7.2.8) block vectorization outright.
- **No aliasing through pointers.** Ch. 10's linear-time results assume reference parameters, no pointer variables, and a two-level (global/local) name space. Ch. 10 says plainly that alias analysis for C is flow-sensitive and therefore intractable in the general case.

Cost. Dependence testing is the cheap part when partitioned; Triolet measured Fourier-Motzkin at 22 to 28 times the cost of conventional tests. The expensive part is the transformation search. Minimum critical edges for node splitting, minimum breaking conditions, minimum loop selection, multi-type fusion order, and register bin packing are each NP-complete or NP-hard, and the book's consistent answer is: predict the effect on the dependence graph, do not transform the program until you have decided.

Where it fails outright. Vectorization gains nothing when the loop is a recurrence and no transformation breaks it. Ch. 5 §5.11 is a candid list of ways a *legal, maximal* vectorization loses: non-unit stride against banked memory, scatter-gather, trip counts of three or four (graphics and chemistry codes), vector divide, and conditional execution under mask. Skewing produces triangular iteration spaces with average vector length N/2 and per-iteration bound recomputation. Loop distribution inserts a barrier. Scalar expansion costs memory. There is no transformation here whose profitability is unconditional.

# Relevance

**Stage 07 is where this lands, and it directly fills the known SSA Book hole.** The SSA Book's chapter 10 has two unrendered figures in exactly the induction-variable stride-detection walkthrough. Chapter 4 §4.5 of this draft covers that material completely and in a formulation that does not depend on those figures. `IVSub` (Figure 4.8) is a full algorithm: require that the candidate statement dominate the loop exit with respect to loop entry, so it executes every iteration; require exactly one self-edge in the def-use graph, so the variable is updated every iteration; require the controlling operation on the self-referencing expression to be addition and the remaining expression `cexpr` to be addition or subtraction of a loop-invariant quantity, negating `cexpr` in the subtraction case; then replace each use, using multiplier `((I-L)/S)*cexpr` for uses textually *before* the definition and `((I-L+S)/S)*cexpr` for uses *after*; then move the statement out of the loop as `iteration_count * cexpr`. The subtle part, which the SSA Book's figures were presumably illustrating, is graph repair: the induction self-edge must be *retained* unless a `blocking_definition` (an unconditional reassignment such as `K = 0` earlier in the enclosing loop) provably stops the old value from reaching around, and `blocking_definition` must return true only when it can positively guarantee that.

The driver `IVDrive` gives us the ordering rule as well: forward-substitute first (it creates new inductions), then substitute inductions **inside out** (an inner substitution creates a new induction on the outer loop), and normalize *before* substituting or you emit an integer divide and multiply inside the loop that strength reduction cannot remove and dependence testing cannot digest. Two independent formulations of stride detection is a better position than one with missing figures, and A&K's runs on def-use chains rather than SSA. Their own SSA construction section (§4.4.4) is an unwritten placeholder, so it is genuinely complementary rather than redundant.

**Stage 10.** This is the loop-based vectorization tradition and it is the counterweight to Larsen and Amarasinghe. Read together, the comparison is sharp. SLP's four claimed advantages (robustness, scalability, simplicity, portability) are exactly the four places this book documents pain: profitability decisions that are individually NP-complete, whole-nest global analysis, an interaction matrix among nine transformations, and a hard dependence on loops-over-arrays. What SLP *cannot* replace is the dependence machinery itself. Larsen and Amarasinghe still need to prove independence before packing two statements, and this book is where that proof comes from. The right reading for us: take dependence testing and induction variable substitution from A&K, take the packing algorithm from SLP, and skip `codegen`.

Concretely for a Scheme compiler:

- **Bytevector and f64vector indices are our subscripts.** After induction variable substitution and constant propagation, a `do` loop over an `f64vector` produces exactly the strong-SIV shape the fast path is designed for. Weak-zero SIV telling us to peel iteration one, and weak-crossing SIV telling us to split at the crossing point, are both cheap and both directly applicable to reversal and reduction kernels.
- **`05-intervals` and dependence testing want the same facts.** Ch. 10 §10.2.7.1 makes range analysis a variant of interprocedural constant propagation over a range lattice with a bounded-widening finite descending chain. Our interval domain is already that lattice. The example given (proving `K ∈ [0:1]` eliminates a dependence) is precisely what our stage-05 output can supply to stage 07, and it argues for running intervals before dependence testing rather than after.
- **Scalar replacement (ch. 8) is stage 08 and 12 work, not stage 07.** The transformation converts `(vector-ref v i)` reloads into a named temporary that the register allocator can color. For unboxed flonum vectors this is the difference between a load per operation and a load per cache line, and the pruning-via-typed-fusion formulation means we get it from machinery we need anyway.
- **The `mark_loop` / `transcode` split is the architectural lesson.** Decide on the dependence graph; mutate the program once, at the end, only for the transformations that survived selection. That is the right shape for a nanopass compiler and it is the opposite of the fold-transformations-into-one-pass instinct.
- **Ch. 10 is largely not for us.** Whole-program MOD/REF for reference parameters is a Fortran problem. What transfers is the classification (flow-sensitive vs flow-insensitive, propagation vs side-effect), the jump-function formulation of interprocedural constant propagation, and the empirical result on inlining: Cooper, Hall and Torczon measured a systematically inlined program taking 95 hours to compile and running *slower*, because downstream optimizers handle inlined code badly. That is an argument for selective, goal-directed inlining and for procedure cloning, which is the more interesting idea and the one Chez-style specialization already resembles.

**One claim to weigh carefully.** Ch. 8's measured speedups are strong on kernels (matrix multiply 3.07, Gmtry 5.98, convolution 2.22, LU 2.35) and weak on whole applications (1.01 to 1.11, one outlier at 4.5 for Matrix300, which SPEC subsequently *removed from the suite* because compilers were optimizing it this way). The book says so directly. Treat the kernel numbers as the honest ceiling for a hot loop and the application numbers as the honest expectation.
