# Contribution

**Slug correction first, see Notes: this file is Keep's dissertation, not the ICFP 2013
paper of the same name.** The ICFP paper is already in the bundle as
`keep-dybvig-nanopass-preprint`. This document covers only what the dissertation adds.

The dissertation's thesis is a rebuttal. In 2004 Sarkar, Waddell, and Dybvig submitted the
nanopass idea to ICFP positioned as a tool for commercial compiler development; the reviewers
accepted it only after it was repositioned as educational. Keep concedes they were right
about the prototype (Sarkar implemented 20 of ~50 class-compiler passes and never finished
the register allocator or code generator) and then does the experiment properly: rebuild the
Chez Scheme back end as a drop-in replacement using an improved framework, and see what it
costs. Answer: ~50 back-end passes over ~35 intermediate languages replacing 5 multipurpose
passes, generated code 15.0-26.6% faster, compile time 1.64-1.75x slower. Built in about a
year and a half. It passes Chez's full regression suite and bootstraps.

Two thirds of the document is not in the ICFP paper: the complete `define-language` /
`define-pass` specification (Chapter 2, ~50 pages), R6RS cross-library optimization
(Chapter 4), and the flat-closure optimization algorithm (Chapter 5).

# Mechanism

## The framework (Ch. 2)

`define-language` takes terminals (each needs a lexically visible `name?` predicate) and
nonterminals with meta-variables and productions. Meta-variables carry suffixes (`*`, digits,
`?`, `^`) that are pure naming; the `...` ellipsis is what means "list". `(maybe x)` means the
field is `x` or `#f`. Productions are keyword-led S-expressions, bare meta-variables (which
subsume one nonterminal into another), or implicit forms. A `=>` clause gives a pretty form
for the unparser so the term can be evaluated in the host Scheme.

Products: the language definition itself (a compile-time value), an unparser, predicates,
and internally a meta-parser plus a **record type per production**. Records, not S-expressions
or tagged vectors; dispatch is on an integer tag with `fx=?`, upgraded from the prototype's
record predicates.

Language extension is the load-bearing convenience. `(extends L0)` plus `(- ...)` / `(+ ...)`
clauses inside `terminals` and each nonterminal. Removing all productions of a nonterminal
deletes it. `diff-languages` recovers the extension form between any two languages;
`language->s-expression` prints the full expansion. With ~35 languages this is the only way
the source stays readable.

`define-pass name : Lin (fmls) -> Lout (extra-returns)` with a `definitions` clause, a set
of transformers, and a body. A transformer is
`(name : NTin (fmls) -> NTout (extra-returns) clauses)`. Three escalating levels of
boilerplate removal, all shown on the same `convert-complex-datum` pass:

1. Explicit recursive calls in every clause.
2. **Catamorphisms**: `,[e]` in the pattern means recur. Under an ellipsis it becomes `map`.
   The target transformer is resolved by matching input nonterminal type, output nonterminal
   type, extra arguments, and extra return values; if nothing matches and no args or extra
   returns were specified, a transformer is **autogenerated on demand**.
3. **Clause autogeneration**: write only the clause that changes. Everything else is filled
   in. In the example this collapses ten clauses to one guarded `quote` clause.

Details that matter when writing real passes:

- Extra formals thread analysis state. They are matched **by name** between calling and
  target transformer, so a `set*` formal propagates through autogenerated clauses silently.
  Defaults `[fml init]` fill in when no matching formal exists.
- Autogeneration of *transformers* is deliberately restricted to those with a single input
  and single output and no extras, "to help reign in some of the unpredictable behavior."
  `finalize-locations` is the example where you must write six empty transformers by hand
  because they need an `env` argument.
- `*` in place of a language means no input term (parsers) or no output term (the x86-64
  emitter, and the `everybody-home?` predicate that returns a boolean).
- Terminal transformers exist and are just Scheme expressions. Adding them was driven by the
  Chez rewrite and shrank the `cpsrc` pass from 87 lines to 55.
- `else` suppresses autogeneration for that transformer.
- `with-output-language (L n)` rebinds quasiquote outside a pass; it is a splicing form and
  therefore *cannot* be sugar for `define-pass`. `nanopass-case` matches outside a pass and
  *is* sugar for `define-pass`.
- Templates are per-field, not per-S-expression. `(letrec ([,bindings ...]) ,body)` is
  illegal; you must write `(letrec ([,(map car bindings) ,(map cadr bindings)] ...) ,body)`.
  Deliberate, so the cost of destructuring is visible.
- Debugging: `echo-define-pass` and a per-transformer `echo` keyword dump the expansion;
  `trace-define-pass` and a per-transformer `trace` keyword unparse input and output terms at
  run time. Both exist because autogeneration can silently shadow a hand-written transformer,
  which the dissertation reports actually happening during the Chez rewrite.

Prototype-to-new differences worth knowing: language definitions are no longer restricted to
top level (the meta-parser moved from an `eval`-retrieved meta-definition into the
compile-time environment); passes take extra arguments and return extra values; passes can
enter at a non-entry nonterminal; the prototype's *combining procedures* for extra return
values were **removed**, because a commercial compiler threads values through and mutates
fields on variable records rather than merging lists.

## The two compilers compared (Ch. 3)

Original Chez back end: `cp1`, `cpr0`, `cpr1`, `cpr2`, `cp2`. Linear-scan register allocator
with lazy save/restore; primitive expansion deferred to code generation, which costs two or
more reserved registers.

New back end: graph coloring with move biasing, which forces near-assembly expansion far
earlier and forces a full live analysis to build the conflict graph. The payoff is more
registers exposed (decisive on 32-bit x86's eight), tighter frame packing, fewer
frame-to-frame moves. The dissertation names it "the biggest contributing factor, and the one
that is consistent in all of the benchmarks" for the run-time win. It is also where the new
compiler **loses**: instead of lazy save, it uses a heuristic estimating save/restore cost
against permanent spill cost, and Keep says plainly this underperforms the original.

Other back-end differences: the consumer of a multiple-value producer can now be pushed into
the tails of an `if` by labeling the consumer and jumping to it, which the original could not
do without duplicating code; chained multiple-value calls position return values in
argument order. Missing relative to the original: Sparc and PowerPC, and block allocation of
closures.

## Cost accounting, the part everyone skips

- Front end (same algorithms, only the representation differs): **0.96-1.03x**. The nanopass
  record representation is not slower than Chez's tagged vectors.
- Back end: **1.91-2.14x**, and that is the graph-coloring allocator, not the pass count.
- `cpsrc`, a trivial linear pass: 1.01-1.06x. `cp0`, the source optimizer, 1.15-1.22x average
  but 0.97-1.15x by total time. Little size change (3687 -> 3571 lines), as expected for a
  pass that is mostly non-matching logic.
- **Traversal overhead 68.5-69.0%.** Measured by autogenerating a dummy pass for each real
  pass and dividing. Two thirds of the time in a typical pass is walking the input and
  building the output, not doing work.
- **Marginal cost of one more pass**, by dummy passes inserted at three points: 0.20-0.26% of
  back-end time before primitive expansion, 0.53-0.62% after primitive expansion, **2.18-2.20%
  after instruction selection**. An order of magnitude spread. Passes are cheap early and
  expensive late, because the term has expanded.
- Compile-time ratio does **not** correlate with program size (Fig. 3.13). Some of the worst
  ratios are the shortest benchmarks. Unexplained.

## Closure optimization (Ch. 5)

The most reusable chapter. Preconditions: no assigned variables (assignment conversion),
`letrec` pure and binding only lambdas (letrec purification), lambdas nowhere else, unique
names.

**Classification.** A procedure is *known* at a call site if that site provably invokes only
its lambda. It is *well-known* if its value is used only at sites where it is known. The
analysis is a single linear pass: fresh label per letrec lambda, optimistically mark
well-known, and demote to not-well-known on any reference outside call-operator position.

**Representation, by well-knownness and free-variable count:**

| case | representation |
|---|---|
| well-known, 0 fvs | nothing; closure eliminated |
| well-known, 1 fv `x` | the value of `x` itself |
| well-known, 2 fvs | a **pair** (2 words vs a closure's 3) |
| well-known, >=3 fvs | a **vector** (same size as a closure, but a small length beats a full-word code pointer, and vectors can be shared) |
| not-well-known, 0 fvs | statically allocated constant closure |
| not-well-known, >=1 fvs | real closure |

**Free variables that can be dropped:** unreferenced ones (created when a closure is
eliminated), globals (address goes in the code stream), constants, aliases, **self-references**
(a link at a fixed offset that always points back to itself is useless), and **unnecessary
mutual references** (`even?`/`odd?` referencing each other only to hand over closures).

**Sharing**, two safe cases. (1) Same lifetime, at most one code pointer needed: approximated
by strongly connected components of the free-variable graph within a `letrec`. (2) Same free
variables, no code pointers: safe across unrelated bindings because the shared closure retains
no more than each original retained indirectly. The space-safety argument is the whole
constraint; the third, subtler hazard is retaining a *code pointer* too long, which matters
only because Chez generates code at run time via `eval` and therefore collects code.

**Borrowing.** A compile-time `bank` maps free-variable sets to representative variables of
pair/vector closures from enclosing `scletrec`s. A new closure with a compatible set borrows
instead of allocating. Closures with code pointers are never deposited. Entries are withdrawn
when processing a lambda body where the name is not free.

**Algorithm shape:** gather free variables and well-knownness; partition each `letrec` into
SCCs (`scletrec`); choose sharing subsets (one subset per not-well-known binding, all
well-known bindings lumped with an arbitrary one); compute required free variables via an
**outermost-to-innermost** traversal with an environment `rho : Var -> Exp + bottom`; select
representations; rebuild into `labels` plus explicit `cp` parameters and
`closure-ref`/`car`/`cdr`/`vector-ref` accesses. Cycles among closures in one `scletrec` force
allocate-all-then-`closure-set!`-all. Believed linear in total free-variable count, with a
`seen` flag per variable to avoid set overhead.

**Results:** 56.94% of closures and 44.89% of free variables eliminated statically; 58.25% of
allocation and 58.58% of closure-attributable memory references eliminated dynamically.
Compile time changes by under 1%. Per-optimization breakdown (Table 5.1) is the interesting
part: self-reference elimination alone accounts for 25.41% of free variables and 45.64% of
memory references; mutual references 7.91%/32.55%; representation selection 29.65% of closures
and 20.78% of allocation; **sharing 1.91% and borrowing 0.20%**. The whole is much larger than
the sum, because each enables the others.

## Cross-library optimization (Ch. 4)

Two mechanisms. `library-group` wraps a set of R6RS libraries plus an optional top-level
program into one compilation unit, expanding to nested `letrec*`s with library-global
references rewired to local variables. The hard part is Scheme-specific: procedural macros
mean compiling library B may require *invoking* library A, and a library must be expanded
exactly once (a macro that consults a config file or an RNG could otherwise produce two
incompatible expansions). Solution: expand each library once as if standalone, run its invoke
code through the rest of the compiler if needed for expansion, then merge and rewire. Synthetic
dependency cycles from fusing invoke code are handled by wrapping each library in a
`(lambda (uid) ...)` that returns the next nested lambda as a restart point.

Implicit cross-library optimization, used when `library-group` is not: the expander leaves a
breadcrumb node per export, and the source optimizer fills in a mutable field on the library
global if the result is a *copyable constant* (not a pair/vector/record, since those must stay
`eq?` to themselves) or an *inlinable procedure* (no free variables, no library-global
references, under the score limit measured **before** inlining since the call site is unknown).

Measured: 24% speedup on the MPL symbolic math test (many small cross-library calls),
negligible on matrix multiply (work concentrated inside one library). Both mechanisms give
about the same result on these two programs.

# Applicability

The framework needs `syntax-case` and a compile-time environment; the macros are ~4600 lines.
The closure algorithm needs assignment conversion, letrec purification, and unique names, all
standard. The `library-group` machinery needs procedural macros and an expander you can
modify, which is why the chapter argues it will matter to Dylan, PLOT, and any language that
grows real compile-time metaprogramming.

Known sharp edges, all reported by the author. Autogenerated transformers can silently shadow
hand-written ones, producing errors at compiler run time rather than expand time. Every
language mints distinct record types, so a pass with different input and output languages must
rebuild every node even where nothing changes; the register and frame allocation passes are
called out as the victims. Autogenerated clauses are flow-insensitive, so extra return values
and updated formals are lost on recursion, forcing hand-written boilerplate for any
flow-sensitive pass, which "led to many boilerplate clauses" in the Chez rewrite. The
suggested fixes (polymorphic languages sharing records, flow annotations in language
definitions, pass fusion as deforestation) are all future work.

# Relevance

**The pass-cost numbers are the number to plan against.** Our CUJ has nine stages after
stage 4 and the honest question is what nine more passes cost. The dissertation answers with
measurement rather than intuition: 0.2% of back-end time for a pass near the top, 2.2% for a
pass after instruction selection. Our new passes (5 through 10) all sit *before* instruction
selection, in the cheap region. That is the single most useful fact in the document for us.

The corollary is the 68.5% traversal overhead. Most of a nanopass pass is walking and
rebuilding. If we want a pass budget, the lever is not doing less work per node, it is not
running a full traversal at all, or fusing. Note also that Keep found the front-end record
representation is *not* slower than Chez's hand-rolled tagged vectors (0.96-1.03x), so the
formal-language discipline is free at the representation level; the back-end 2x is entirely
the allocator.

**The closure chapter is directly implementable and we should implement it.** Self-reference
and mutual-reference elimination together are 33% of free variables and 78% of the eliminated
memory references, and they are the two simplest transformations in the chapter. Representation
selection (the pair/vector/single-variable/nothing table) is another 30% of closures for
almost no analysis. Sharing and borrowing are 2% combined and can be skipped in a first
implementation without meaningful loss. That ordering is not obvious from reading the chapter
front to back and it is what Table 5.1 is for.

**The register-allocator finding is a warning shot for stage 12.** Keep replaced Chez's
linear scan with graph coloring, got faster code, doubled back-end compile time, and *lost*
ground on one specific thing: he could not reproduce lazy save with a heuristic. Our plan
picks linear scan. If we later want coloring quality we should expect the same shape of
tradeoff, and we should port lazy save rather than approximate it.

**Sobering calibration.** The full closure optimization moves benchmark run time by an average
of **3.6%**, range negligible to 20%, with a few benchmarks getting slower from cache effects.
Eliminating 58% of closure allocation buys 3.6% wall clock, because Chez's inline allocation
is already about three instructions plus one store per field and because loop recognition has
already removed the closures from the hot loops. Any optimization we propose should be sized
against that ratio before we build it. It also tells us where our opening actually is: not in
allocation, which Chez has squeezed dry, but in the numeric kernels that loop recognition
leaves as tagged, boxed, bounds-checked scalar code.

The framework itself is a reasonable choice for our compiler, and the dissertation is the
manual. The `diff-languages` and `echo`/`trace` facilities are what make 35 intermediate
languages tractable, and they are documented nowhere else at this level of detail.

**Three claims worth flagging as soft.**

The linearity of the closure algorithm is *believed*, not proved: "Although we have yet to
create a proof, we believe that the implementation is linear in the number of variables free in
all lambda-expressions in the program." Footnote 13 concedes that count is worst-case quadratic
in program size (citing Shao and Appel), so "linear" is linear in a quantity that is not linear.

The compile-time-versus-program-size non-correlation (Fig. 3.13) is presented and then
abandoned: "An understanding of why this occurs might lead to overall improvements in compile
time." Something systematic is unaccounted for in the 1.64-1.75x figure.

The garbage collector contaminated the pass timings badly enough that the methodology had to
change mid-study. The `ddd` benchmark showed the `cpsrc` pass 7.97x slower before a forced
maximum collection was inserted before the pass, and one benchmark showed 0.01x because the
*original* compiler happened to collect there. The published per-pass numbers are all
post-workaround. Treat single-benchmark pass timings from this document with suspicion; the
aggregates are fine.

**Two negative results that are more useful than the positives.** Extending closures to hold
multiple code pointers, which would let every SCC share one closure, was measured before being
built: it would affect under 0.1% of `letrec` bindings, and the idea was dropped. And the
prototype framework's automatic combining procedures for extra return values were removed
outright, because a commercial compiler wants to thread state and mutate fields on variable
records, not merge sets. Both are cases of measuring before implementing, which is the habit
worth copying.
