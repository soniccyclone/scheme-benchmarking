# Problem

A thirteen-stage pipeline with an intermediate language per stage. Written by hand, three things
go wrong: traversal and rewriting boilerplate drowns the meaningful transformation, the output
grammars written as documentation are not *enforced*, and the pass count costs compile time. The
question is what the discipline costs and whether the enforcement is real.

# Three documents, three works

They share titles and will merge under any title-keyed bibliography, so cite them distinctly.

- `keep-dybvig-nanopass-preprint` is the **ICFP 2013 paper**, *A Nanopass Framework for Commercial
  Compiler Development*, Keep and Dybvig, 7 pages, author preprint dated 2013/9/20. It carries the
  framework-plus-evaluation argument.
- `keep-a-nanopass-framework-for-commercial-compiler-developm` is **Keep's 170-page PhD
  dissertation**, Indiana University, December 2012, single author, with the *identical title*. It
  is cited by the ICFP paper as reference [14]. Chapter 2 is the full framework specification,
  Chapter 4 is cross-library optimization, Chapter 5 is the flat-closure optimizer; none of that
  exists in the paper.
- `sarkar-waddell-dybvig-a-nanopass-infrastructure-for-compil` is **not** the ICFP 2004
  *Infrastructure* paper the slug names. The title page reads *A Nanopass Framework for Compiler
  Education*, an Educational Pearl under consideration for JFP, a later expanded version with
  different pagination. Anyone citing this file as "ICFP 2004, pp. 201-212" cites a document with a
  different title.

# Mechanism

**`define-language` is a context-free grammar.** Terminals, each needing a lexically visible
`name?` predicate. Nonterminals with meta-variables and productions. Three production shapes: a
bare meta-variable (`x`, which subsumes one nonterminal into another), a keyword-led S-expression
(`(if e0 e1 e2)`), and an implicit form with no keyword. Keywords only in head position, and at
most one alternative per nonterminal may be a parenthesized form without one, that slot being spent
on application so calls get natural S-expression syntax. Meta-variable suffixes are pure naming;
the `...` ellipsis is what means list. `(maybe x)` means the field is `x` or `#f`. `=>` attaches a
pretty form used by the generated unparser. Products: a compile-time language value, a parser, an
unparser, predicates, and internally a **record type per production**, dispatched on an integer tag
with `fx=?`.

**`extends` is what makes 35 languages affordable.** Only the delta is written:

```scheme
(define-language L1 (extends Lsrc)
  (terminals (- (datum (d))) (+ (constant (c))))
  (Expr (e body) (- (quote d)) (+ (quote c))))
```

Removing the `datum` terminal unbinds the meta-variable `d`, so a stale `(quote d)` production left
behind anywhere is a compile-time error rather than a latent bug. That is the enforcement, and it is
the whole reason to use the framework. `diff-languages` recovers the extension form between any two
languages and `language->s-expression` prints the full expansion.

**`define-pass name : Lin (fmls) -> Lout (extra-returns)`** with a `definitions` clause, one
transformer per nonterminal pair, and a body. Three escalating levels of boilerplate removal, all
demonstrated on the same `convert-complex-datum` pass: explicit recursive calls in every clause;
then **catamorphisms**, where `,[e]` in the pattern means recur, becoming `map` under an ellipsis,
with the target transformer resolved by matching input nonterminal, output nonterminal, extra
arguments and extra return values, and autogenerated on demand if nothing matches; then **clause
autogeneration**, where you write only the clause that changes. In the worked example that collapses
ten clauses to one guarded `quote` clause.

Details that matter when writing real passes. Extra formals thread analysis state and are matched
**by name** between calling and target transformer, so a `set*` formal propagates silently through
autogenerated clauses; defaults `[fml init]` fill in where no matching formal exists.
Autogeneration of *transformers* is restricted to those with a single input, single output and no
extras, "to help reign in some of the unpredictable behavior." `*` in place of a language means no
input term (parsers) or no output term (emitters, predicates). Templates are per-field, so
`(letrec ([,bindings ...]) ,body)` is illegal and the destructuring must be written out,
deliberately, so its cost is visible.

**The pass taxonomy from 2004, most often dropped from later summaries.** Simplification (translate
into a simpler language), verification (check invariants the grammar cannot express), conversion
(make explicit an abstraction the target lacks), analysis (record information as annotations), and
improvement (reduce run time). Verification and improvement passes have the *same* input and output
language, which is exactly what makes them individually switchable: verification runs only during
compiler development, and improvement passes can be disabled for compile-time speed or for
regression testing where an optimization masks a bug elsewhere.

**The `=>` translates-to property is load-bearing and the 2013 description drops it.** Because every
production has an implicit or explicit translation into Scheme, the output of *any* pass can be
evaluated and compared against the reference implementation. The 2004 test driver does exactly
that. A differential test harness for free, and far stronger than "the final binary works."

# Preconditions

A host language with procedural macros and a compile-time environment. The framework is a
`syntax-case` DSL, about 4600 lines of macros, and there is no runtime interpretation cost. Nothing
is saved at the boundaries: a code generator "must explicitly handle every grammar element," so
savings are proportional to how much of the language a pass ignores.

Known sharp edges, all reported by Keep. Autogenerated transformers can silently shadow hand-written
ones, producing errors at compiler run time rather than expand time; `echo-define-pass` and
`trace-define-pass` exist because this happened during the Chez rewrite. Every language mints
distinct record types, so a pass with different input and output languages rebuilds every node even
where nothing changes, with the register and frame allocation passes named as victims. And
autogenerated clauses are flow-insensitive, so extra return values and updated formals are lost on
recursion, forcing hand-written boilerplate for any flow-sensitive pass, which "led to many
boilerplate clauses" in the Chez rewrite. That last one lands directly on our stages 05 and 06.

# Cost

The experiment: replace the five back-end passes of the 10-pass Chez compiler with roughly 50
nanopasses over roughly 35 intermediate languages, keep 100% compatibility. Compile time 1.71/1.75x
(x86/x86-64 at optimize level 2) and 1.64/1.71x at level 3. Generated code 15.0 to 26.6% *faster*.
The decomposition is the useful part and it is only in the dissertation.

- Front end, same algorithms and only the representation differing: **0.96 to 1.03x**. The nanopass
  record representation is not slower than Chez's hand-rolled tagged vectors. The formal-language
  discipline is free at the representation level.
- Back end: **1.91 to 2.14x**, and that is the graph-coloring register allocator, not the pass count.
- **Traversal overhead 68.5 to 69.0%**, measured by autogenerating a dummy pass for each real pass.
  Two thirds of a typical pass is walking the input and building the output.
- **Marginal cost of one more pass**, measured by inserting dummy passes at three points:
  0.20 to 0.26% of back-end time before primitive expansion, 0.53 to 0.62% after primitive
  expansion, **2.18 to 2.20% after instruction selection**. An order of magnitude spread. Passes are
  cheap early and expensive late, because the term has expanded.

Two regressions are disclosed in the rewrite: block allocation of closures is missing, and the new
allocator replaces lazy saves with a heuristic that "sometimes underperforms the original."

# Disagreements

**Steele's post-mortem on RABBIT, page 174, argues against fine-grained IR node types, and he
invented this style of compiler.** Splitting `CLAMBDA` from `CONTINUATION` and `CCOMBINATION` from
`RETURN` into distinct data types "was somewhat of a design error." The dichotomy is real
semantically, but it forced a great deal of pass-two code to be written twice over near-identical
shapes. His recommendation is one structure with a discriminating flag. This cuts directly against
what `extends` makes easy: adding a production costs one line, so the temptation to refine is
structural rather than occasional, and the cost shows up two passes later as duplicated
transformers. Prefer one node with a field over two nodes whose passes diverge in a line or two.

**The compile-time overhead is unexplained at the individual level.** The 1.64 to 1.75x average
hides a per-benchmark range of 1.00x to 4.73x, and the authors checked whether the outliers
correlate with expanded source size and found *no direct relationship*. They say plainly they do not
understand why, and that understanding it "might lead to overall improvements." Some of the worst
ratios are on the shortest benchmarks. That is an unexplained result sitting in the middle of the
paper's central claim, and it means a 4x-slower compile on one of our benchmarks is a known
phenomenon rather than necessarily a bug in our passes.

**The comparison is not apples-to-apples and they say so.** They lacked the resources to build a
second nanopass compiler matching the old one's function, so the 1.75x bundles nanopass overhead
with a deliberately slower graph-coloring allocator. The nanopass tax alone is unmeasured, and the
0.96-1.03x front-end figure is the closest available proxy.

**The speedup is not attributable to nanopass.** "Produces faster code than the original, averaging
15-27%" is true, and the paper attributes it to the graph-coloring register allocator with move
biasing, improved closure optimization and cross-library optimization. Nanopass made the rewrite
*feasible*; it did not make the code fast. The similix and softscheme benchmarks got 1.22 to 1.54x
*slower* because they invoke the compiler at run time, reported honestly and cutting the other way.

**Compile time was the objection and fusion was the proposed answer; the answer was never needed.**
The ICFP 2004 committee accepted the original paper only after it was repositioned as education,
because they did not believe many-small-passes could survive commercial compile-time budgets. The
2004 remedy proposed was a pass combiner using deforestation to fuse passes on demand. As far as the
record shows it was never built. Keep and Dybvig answered empirically instead. Read together, the
objection was reasonable and wrong: compile time really is the risk, it really did cost 1.7x, and
that was affordable.

**Two mechanisms were removed between generations, which is information.** The prototype's automatic
*combining procedures* for extra return values were dropped, because a commercial compiler threads
values through and mutates fields on variable records rather than merging lists. And the `void` and
`datum` output languages became "passes with no output language." Both were measured or exercised
before being cut.

**One class of optimization does not fit.** Click's GVN deliberately produces an *illegal* program,
instructions placed nowhere, repaired by a following code-motion pass. A pass whose output is
provably incorrect until a later pass repairs it cannot be typed honestly in this framework; the
output language would have to admit unplaced instructions, which is the sea of nodes, not a Scheme
core language. If we want that architecture the honest encoding is a distinct intermediate language
where placement is genuinely optional, not a fudge in `Lcore`.

**Syntax drift across the three documents is significant.** The 2004 surface syntax
(`(define-language L over (x in var) where ...)`, `(define-pass p L1 -> L2 ...)`, `void`/`datum`
output languages) is not what `nanopass-framework-scheme` ships. Read 2004 for the methodology and
2012/2013 plus the library source for the syntax.

# For us

The framework is the compiler, so the mechanism section above is specification rather than
background. Four decisions follow.

Define `Lcore` once and make every later stage an `extends` delta. `declare` and `policy` should be
*removed* by the grammar delta at the stage that consumes them, so any later pass still mentioning
them fails at expansion time. That is the mechanism by which "the policy lives in the environment
threaded through the passes, not in a global parameter" gets enforced rather than merely intended.

Interval and pentagon facts ride as *extra return values*, not as annotations in the grammar. If we
find ourselves adding an `absval` field to a production, we have chosen wrong. Be ready for the
flow-insensitivity of autogenerated clauses to force hand-written transformers in stages 05 and 06;
Keep hit exactly this and named it.

Add verification passes, which our CUJ currently lacks. `L -> L`, disableable, seven of them in the
2004 course compiler. After stage 04, verify every `declare` premise names a bound variable; after
stage 06, verify no check survives that the domain claimed to prove; after stage 09, verify every
claimed non-aliasing pair traces to distinct allocation sites. And use `=>` translates-to from stage
03 onward if the shipping library still supports it, so every pass's output can be run under Chez
and diffed against the reference.

Budget with Keep's numbers rather than intuition. Our new stages 05 through 10 all sit *before*
instruction selection, in the 0.2 to 0.6% region, so nine more passes is a few percent, not a
doubling. The 68.5% traversal overhead says the lever on pass cost is not doing less work per node,
it is not running a full traversal at all. And the 2004 course compiler's decomposition is a closer
model for our phase 7 than the Chez back end is, because someone has actually taught it: eleven
passes for closure conversion, four for lazy saves. That is the granularity target.
